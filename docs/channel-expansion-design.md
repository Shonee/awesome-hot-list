# 热榜渠道扩展设计

## 1. 目标

在不引入浏览器自动化的前提下，接入第一批与第二批热门资讯渠道，并对 Google Trends、Bing、快手、Hugging Face 做 GitHub Actions 网络验证。新增渠道必须提供可解析的有效榜单；不可达或结构不稳定的候选不会以空卡片占位。

## 2. 数据源策略

每个渠道按“官方公开接口或页面 -> 稳定第三方榜单 -> RSS”选择数据源。本轮渠道均优先使用非 RSS 数据；只有官方与第三方均不可用且用户允许时才聚合到 RSS 卡片。第三方源必须记录 `providerName`、`providerUrl`，并共享进程级缓存、最小请求间隔和 403/429 冷却机制。

## 3. 渠道方案

- 百度热搜：解析官方实时榜页面内的结构化 `s-data`。
- 网易新闻：使用官方移动端热闻 JSON 接口。
- 新浪：一个卡片包含“新闻热榜”和“财经热榜”，解析官方榜单接口返回的 JavaScript 数据。
- 东方财富：使用官方人气榜接口，并以一次批量行情请求补齐股票名称和涨跌幅。
- Hacker News：使用官方 Firebase API，只读取榜单前 30 个条目，展示前 20 条；从 RSS 默认源中移除，避免重复。
- 澎湃新闻：使用官方首页侧栏结构化接口并过滤栏目节点。
- Lobsters：使用官方 `hottest.json`。
- Hugging Face：实现官方 Trending API 适配器，但只有 Actions 验证可达且数据有效后才默认启用。
- 快手：优先解析官方页面的 Apollo 状态，失败时使用 DailyHot API；第三方请求采用独立限频与冷却策略，是否默认启用由 Actions 验证结果决定。
- Google Trends：Actions 中验证官方 Trending 页面或结构化响应，只有能持续解析出有效条目才接入。
- Bing：仅在找到可验证、稳定、合法的榜单源时接入。已退役的 Bing Search API 和普通搜索结果页不作为热榜源。

## 4. 调度与展示

默认小时渠道为百度、网易、新浪、澎湃、Lobsters。东方财富与 Hacker News 使用较低频率；Hugging Face、Google Trends、快手按 Actions 结果进入特殊调度。所有通过验证并启用的新增渠道默认显示、进入综合报告；实验性或未验证渠道不注册为默认卡片。

## 5. 稳定性约束

解析器要求至少返回合理数量的有效条目，否则按失败处理并保留上次成功快照。失败且没有历史有效榜单的渠道应在下一次调度立即重试，不被旧 `fetchedAt` 阻塞。网络探测必须验证响应结构和有效条目数，而非只检查 HTTP 状态或响应字节数。

## 6. 成功标准

- 所有确定渠道具备解析器单元测试、注册表测试和失败隔离行为。
- 第三方回退具备限频、缓存和 403/429 冷却测试。
- GitHub Actions 探测报告明确列出 Google、Bing、快手、Hugging Face 的可达性与有效条目数。
- 全量测试、Python 编译、工作流 YAML 解析和差异检查通过。
- 新增渠道经真实采集后能写入 `latest.json`，页面和报告渲染不回归。
