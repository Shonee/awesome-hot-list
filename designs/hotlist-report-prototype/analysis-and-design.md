# `hot-newss` 参考分析与热榜原型设计方案

## 1. 分析范围

- 参考仓库：`Shonee/hot-newss`
- 参考提交：`001595d508aeb063fb355d15693ddffedab0b8d0`（2026-04-01）
- 参考文件：`index.html`、`hot_news_data.json`、`README.md`
- 当前交付范围：只优化 `designs/hotlist-report-prototype/index.html` 原型，不改生产页面、采集器和聚合脚本。

## 2. `hot-newss` 提供了什么

该仓库本质上是一个静态数据快照和单页展示器，不包含各渠道的采集实现。页面中的“刷新”只会重新读取同目录的 `hot_news_data.json`，不能直接作为新增渠道的数据源。

### 数据覆盖

参考数据包含 14 个来源：知乎、RSS、抖音、微博、今日头条、哔哩哔哩、AcFun、IT之家、豆瓣小组、虎扑、36氪、同花顺、脉脉、雪球。当前项目另有 GitHub，因此原型按 15 个候选渠道设计。

需要注意一个原始数据命名问题：IT之家条目的 `source` 是 `baidu`，但展示标题是“IT之家”。整合时应统一为稳定 ID `ithome`，不要继承这个错误标识。

### 可借鉴的数据字段

渠道级字段：

- `source`：渠道稳定标识
- `title`：渠道展示名
- `subtitle`：榜单名称数组，一个渠道可有多个榜单
- `updateTime`：渠道数据更新时间
- `items`：该渠道全部榜单项

条目级字段实际出现过：

- 必需：`rank`、`title`、`url`
- 榜单归属：`type`
- 热度与来源：`hot`、`source`
- 时间：`timestamp`、`datetime`、`createtime`
- 富媒体：`image`、`pic`、`desc`

其中热度和时间字段格式不统一，不能直接作为当前项目的正式契约。接入时应在渠道适配层完成标准化。

### 可借鉴的页面行为

- 以渠道为卡片，一行 4 列的高密度浏览。
- 通过 `subtitle + item.type` 在同一渠道内切换多个榜单。
- 榜单正文固定高度并独立滚动。
- 长标题最多显示两行，悬停可查看完整标题。
- 前三名有明显但克制的排名强调。
- 卡片同时显示来源、榜单、更新时间和条目热度。

这些思路已经以当前原型的设计语言重新实现，没有复刻参考页面的 Tailwind 类名、结构代码或视觉品牌。

## 3. 不应直接搬入的内容

- 参考仓库没有 `LICENSE`。默认版权约束下，不应直接复制其源码或整份数据文件，只借鉴信息结构和交互思路。
- 页面依赖 Tailwind CDN 和 Font Awesome CDN，不适合当前项目的零构建、低依赖目标。
- 页面包含百度统计和 Google Analytics；当前项目不需要引入第三方追踪。
- 公告使用 `innerHTML` 注入 JSON 内容；若数据可被外部影响，会形成 XSS 风险。
- 条目标题、URL 和图标类名也通过模板字符串写入 DOM，缺少统一的内容和 URL 校验。
- 外部图片可能带来隐私、可用性和防盗链问题，应使用明确的图片代理或禁用默认远程图片加载。
- “刷新”只是重新获取静态 JSON，不能替代采集任务状态、失败信息和数据时效判断。

## 4. 当前项目已有能力

当前项目不需要用 `hot-newss` 的扁平 JSON 替换已有数据。以 `archived/bilibili/data.json` 为例，现有聚合结果已经包含：

- 热门搜索、全站热门视频、视频排行榜三个榜单。
- 每个榜单的完整时间切片。
- `top_stable`、`biggest_risers`、`biggest_fallers`。
- `new_entries`、`exit_entries`。
- 可用于今日报告和历史报告的日内趋势数据。

因此正确的整合方向是：保留当前时间序列与报告能力，新增统一展示契约和缺失渠道适配器。`hot-newss` 只能补充渠道清单、字段线索和多榜单展示方式。

## 5. 推荐统一数据契约

最新热榜和日报应使用不同层级，但共享渠道、榜单和条目结构：

```json
{
  "schemaVersion": 1,
  "generatedAt": "2026-09-04T13:00:00+08:00",
  "channels": [
    {
      "id": "bilibili",
      "name": "哔哩哔哩",
      "sourceUrl": "https://www.bilibili.com/",
      "updatedAt": "2026-09-04T12:11:00+08:00",
      "status": "ok",
      "rankings": [
        {
          "id": "hot-search",
          "name": "热门搜索",
          "items": [
            {
              "rank": 1,
              "title": "示例标题",
              "url": "https://example.com/item",
              "hot": 1291356,
              "description": null,
              "imageUrl": null,
              "publishedAt": null
            }
          ]
        }
      ]
    }
  ]
}
```

约束建议：

- `channel.id` 和 `ranking.id` 使用稳定英文 ID，展示名可调整。
- `updatedAt`、`generatedAt` 统一为带时区的 ISO 8601。
- `hot` 保留原始数值或 `null`，展示层再格式化；原始字符串另存 `hotLabel`。
- URL 只允许 `http:`、`https:`，渲染时统一转义文本和属性。
- 同一渠道的多个榜单必须分别保存条目，避免依赖条目中的自由文本 `type` 做运行时分组。
- 日报继续保存时间切片和变化摘要，不把这些字段塞进“最新快照”对象。

## 6. 多榜单交互方案

原型采用两级结构：

1. 渠道是固定排序的主要容器。
2. 渠道内部有多个榜单时显示榜单 Tabs；只有一个榜单时不占用额外高度。

哔哩哔哩原型展示“热门搜索 / 全站热门视频 / 视频排行榜”三个榜单。切换状态按渠道记录在 `activeRankings`，刷新后仍保持。每个榜单仍遵循用户配置的 10/20/30/50 条限制，最长不超过 50。

榜单切换只替换当前渠道内容，不改变渠道顺序，也不影响其他渠道的榜单选择。这样既保留图片中清晰的多榜单入口，又与当前原型的边框、字号、颜色和密度保持一致。

## 7. 主题与布局扩展方案

主题和布局是两个独立维度：

- 主题只负责颜色、前景、边框、状态色和阴影等视觉 token。
- 布局只负责渠道容器如何排列和切换，不修改数据结构。

当前原型提供：

- 主题：`editorial`（默认编辑部浅色）、`night`（夜间阅读）。
- 布局：`cards`（卡片网格）、`list`（紧凑列表）、`channel-tabs`（渠道 Tabs）。

本地配置结构：

```json
{
  "theme": "editorial",
  "layout": "cards",
  "topCount": 20,
  "order": ["bilibili", "douyin", "weibo"],
  "visible": { "bilibili": true, "douyin": true },
  "activeChannel": "bilibili",
  "activeRankings": { "bilibili": "热门搜索" }
}
```

配置保存在 `localStorage`，读取时会补全新渠道并过滤无效主题、布局和渠道 ID。未来增加主题只需增加一组 CSS token 和一个主题注册项；增加布局只需增加对应布局样式及必要的渲染分支。默认值始终保持 `editorial + cards`。

布局定位：

- 卡片网格：默认，适合同时扫视多个渠道；桌面 3-4 列，窄屏自动降为 1-2 列。
- 紧凑列表：适合逐渠道阅读，渠道信息固定在左侧，榜单内容在右侧。
- 渠道 Tabs：适合只关注一个渠道时使用，顶部切换渠道，正文获得最大阅读宽度。

## 8. 建议整合顺序

### 阶段一：统一展示契约

- 为当前 5 个采集渠道输出统一的渠道/榜单/条目视图模型。
- 保留现有归档结构，在渲染阶段做适配，不先迁移历史数据。
- 加入时间、URL、热度格式和空状态校验。

### 阶段二：落地多榜单和显示配置

- 将原型中的渠道内榜单 Tabs、三种布局和两套主题接入正式页面。
- 持久化渠道显隐、顺序、每榜数量、主题、布局及活动榜单。
- 对配置增加版本号，字段变化时做轻量迁移或回退默认值。

### 阶段三：补充渠道

- 按使用价值逐个增加今日头条、IT之家、36氪、雪球等采集器。
- 每个渠道独立记录采集状态和最后成功时间，单个渠道失败不阻断整页。
- `hot-newss` 没有采集源码，因此每个新增渠道都需要单独验证接口、页面规则和使用边界。

### 阶段四：丰富报告

- 今日报告继续基于当日已有时间切片增量生成。
- 历史报告使用前一日完整切片，复用同一套去重、共振和排名轨迹逻辑。
- 图片、描述等富媒体先作为可选字段，不应阻塞基础热榜和报告能力。

## 9. 原型验收点

- 热点词云、排名轨迹和“值得关注”均可打开关联内容；多条结果通过弹窗选择。
- 哔哩哔哩在同一卡片中切换三个榜单。
- 默认卡片布局桌面显示 3-4 列，榜单正文约 10 条高度并独立滚动。
- 标题最多两行，悬停显示全文。
- 渠道显隐、拖拽/按钮排序、每榜数量、主题、布局和活动榜单均保存在当前浏览器。
- 今日报告和昨日报告使用一致的信息结构和交互逻辑。
